## 1. 怎么比

| 项 | 规则 |
|---|---|
| 速度口径 | **s/Mtok**（每百万训练 token 的秒数）= 窗口内各步耗时之和 ÷ 实际训练的 token 之和（提示 + 回答 + 工具返回）。两边每步训练量不同时，另报每步秒数。 |
| 提速比 | 基线 s/Mtok ÷ 我们的 s/Mtok，大于 1 表示我们快。"少用的时间" = 1 − 1/提速比。 |
| 基线 | 该框架在"**每条样本最多旧 2 个版本**"（陈旧度上限 S = 2；陈旧度 = 生成样本时用的权重比训练时旧几个版本）前提下，我们能调出的最快配置。框架自带的提速开关（异步、partial rollout 等）都打开；基线改自己的配置就能拿到的收益，都算给基线。 |
| 成对 | 一对 = 一次基线运行 + 一次我们的运行，在**同一台机器**上先后跑。两种先后顺序（先我们 / 先基线）数量相同。模型、数据、超参、种子、卡数、训练注意力核（两边都是 FA4）、SGLang 版本都一样。 |
| 窗口 | 去掉开头几步（热身、编译），窗口在跑之前就定好。 |
| 95% CI | bootstrap：每对内两边各自按步重抽，各对比值取几何平均，重抽 4000–10000 次。 |
| 健康检查（两边都做） | 熵；训推 log-prob 差（训练端和推理端对同一 token 算的对数概率之差；我们 ≤ 基线的 1.5 倍、不上升）；起始奖励（前 3 步差 ≤ 0.03）；每步训练 token（差 ±5% 以内）；陈旧度 ≤ 2，按 token 或按调用实测，不只看框架自己的计数；检索延迟探针（无失败、无尖峰）。 |
| 消融 | 从我们的全套里每次去掉一项，同机、两种顺序，至少 2 对（单对波动超过 ±5% 就加到 4 对）。比值 = 去掉后的 s/Mtok ÷ 全套的 s/Mtok，大于 1 表示这一项有用。显著 = 合并后的 95% CI 不含 1（Qwen3-Next 是不含 0%）。 |

### 3.1 汇总

| ASearcher 对 slime（参考） | 1.299× [1.235, 1.355] | 约 23% | 18.97 / 14.70 | 1.233、1.330、1.301、1.333 | 仅供参考 |
| Libra 对 slime | **1.219×** [1.133, 1.310] | 约 18% | 45.81 / 37.51 | 1.150、1.247、1.196、1.308、1.172、1.251 | 检查全过；基线用了我们的 ticket |

### 3.2 逐组：健康检查和说明

**Search-R1 对 slime：1.170×**
- 按每步算：1.176× [1.166, 1.187]。两边每步 token 差 ≤ 0.8%。
- 健康检查全过：前 3 步熵两边都在 1.63–1.77；起始奖励两边都在 0.13–0.15；训推 log-prob 差（slime 自己的指标）两边都是 0.0187–0.0189，平稳；陈旧度最坏两边都是 2；平均回答长度两边 443–447；检索探针 0 失败。

**Search-R1 对 verl：1.002×，打平**
- 按每步算，我们**慢 4.6%**（0.956× [0.928, 0.985]），因为我们每步训得多：总 token 多 4.8%（8 对合算），模型自己写的 token 更多（前 4 对多 6.8%，后 4 对更多）。
- 通过：熵（−5.0% 到 +2.1%）、训推 log-prob 差（0.86–1.14 倍）、首步奖励（差 ≤ 0.027）。
- **没过两项**：8 对里 4 对每步训练 token 差超过 ±5%（+5.2%、+10.5%、+7.3%、+7.1%）；1 对前 3 步奖励差 −0.035（门限 0.03）。
- 可能的原因（方向一致，**未证实**）：基线丢掉超龄样本（每次运行 264–687 条），我们一条不丢。另有一次不计时的基线运行碰巧一条没丢，它每步训的 loss token 落在我们的范围里（未复核）。
- `toolcache` 在这里没生效（一处按位置传参的调用绕过了缓存），tokcache / 路由也没活可干（每题只生成 1 个回答）。所以这次打平说明不了这几个组件有没有用。

**ASearcher 对 verl：1.167×**
- 敏感性，第 2–13 步：1.251× [1.213, 1.292]。有一对 verl 那边第 15 步后回答突然变长（每步 token 是我们的 2.2 倍），长批次每 token 更便宜；去掉这一对是 1.176×。两处都对 verl 有利，所以主数偏保守。
- 我们：陈旧度最坏 2（按调用测）；训推 log-prob 差和按陈旧度分布预测的一致（实测 / 预测 0.92–0.99），全过。
- verl：**陈旧度合规未证实**。verl 自己的标签最坏是 2；我们的分段日志给出的上界是 3，占轨迹的 0.002–0.16%。如果 verl 真的超了，它是靠多用陈旧度变快，对 verl 有利。verl 的训推 log-prob 差没判（只有轨迹级的陈旧度数据）。
- 其他检查：熵、奖励曲线形状一致（起点我们 0.12–0.13，verl 0.15）；两边每步都训 128 × 16；两边都用 FA4。

**ASearcher 对 slime：1.299×，仅供参考**
- slime 并发 256 合规（最坏 2）。4 对里有 1 对"末段 log-prob 差上升"没过（1.59，门限 1.5，在我们这边；同顺序重跑没复现）。去掉这一对：1.298× [1.220, 1.364]。因为 ASearcher 的主基线是 verl，这一行只作参考。

**Libra 对 slime：1.219×**
- 健康检查全过：每次运行 20 步 × 512 条；熵两边 0.27–0.31；训推 log-prob 差两边 0.0131–0.0143，平稳；起始奖励 0.27–0.37；陈旧度最坏两边都是 2；两边都用 FA4。
- 顺序影响：先我们的 3 对 1.150 / 1.196 / 1.172，先基线的 3 对 1.247 / 1.308 / 1.251。两序各 3 对，几何平均把它抵掉了。
- 基线用了我们的 ticket 准入。不用的话，slime 要把并发降到 8 才合规；ticket 相对那个配置是 3.01×（见 5.4，不算进 1.219×）。

**Qwen3-Next 对 verl：1.560×**
- 按每步算：1.548×。顺序：先我们 1.530，先 verl 1.591（区间重叠）。
- 一共开了 6 对，两边各卡死 1 次（verl 卡在 EP all-gather，我们卡在权重同步广播），各剔掉 1 对，剩下两序各 2 对。
- 健康检查（9 项 × 4 对 × 两边）全过：每步 token 差 ≤ 1.37%；首步奖励差 ≤ 0.009；陈旧度最坏 我们 2 / verl 1–2；两边 FA2 回退都是 0；前缀缓存清理失败 0；搜索代理延迟两边一样（p50 0.317 / 0.316 s，p95 1.81 / 1.81 s）。
- 测速前的精度体检（每边 10 步）：

| | 我们 | verl 修补后 | verl 修补前 |
|---|---|---|---|
| 训推 log-prob 差 | 0.0138–0.0142，均值 **0.0139**，不上升 | 偶数步 0.016、奇数步 0.020–0.021，均值 **0.0178** | **0.210** |
| 熵 | 0.754–0.816 | 0.77–0.81 | 0.63–0.67 |
| 奖励（模拟搜索，只看趋势） | 0.480–0.508 | 0.49–0.51 | — |
| 陈旧度最坏 | 2 | 2 | — |

- 说明：
  1. **只测了一个场景**：搜索是模拟的（时快时慢、超时、出错），奖励只看趋势。规模缩小为 2 台训练 + 2 台推理，64 × 8。
  2. **测速时开着 `ws direct`**：后来因为偶发卡死（每 60 次同步 1 次；verl 也每 63 次卡 1 次，原因不明）默认关了，没有重测。整组权重同步组件约值 1%，不显著。
  3. **结果偏保守**：测速时开着 ticket 准入，这个场景关掉它还能快 2.3%，而且仍然合规（见 5.5）。
  4. **两边用"旧"的方式不同**：我们的样本几乎都旧 2 步，verl 约 99.6% 只旧 1 步，都没超限。部分收益可能来自这里，没有单独测。
  5. **还不能拆到组件**：消融里只有预取（+13.5%）和专家重排（+2.7%）显著。第 4 节的分段数字不要和消融结果相加减。
  6. **verl 做了三处本地修补**，没推上游：把新版 SGLang（0.5.21）放到路径最前（旧版在多轮序列上，解码时报的 log-prob 和预填充算的系统性对不上）、配套的适配层、GDN 输出归一化用原始权重（转换工具存的时候有精度损失）。两边用同一份 SGLang。

差距落在哪（基线 − 我们）：
- Search-R1 对 slime：2.67 s/Mtok；65% 在训练（只算回答部分），37% 在等数据。
- Search-R1 对 verl：几乎没有差距；训练我们快 0.99 s/Mtok，生成慢 0.91 s/Mtok，所以打平。
- ASearcher 对 slime：4.27 s/Mtok，81% 在等数据。Libra：8.30 s/Mtok，83% 在等数据。
- ASearcher 对 verl：每 token 训练我们反而慢一点（verl 回答变长的那一对让它每 token 训练更便宜），快在生成和同步。

另外两点观察，只在这几个任务上成立：
- **ticket 准入只在"单纯限并发守不住上限"时有用**：Libra、ASearcher 需要；Search-R1 上没影响（×0.996）；Qwen3-Next 上反而慢 2.3%。
- **同步快了不一定有用**：Qwen3-Next 上关掉引擎钩子，同步时间翻倍，整步却没变，因为同步和等数据是同时进行的（未复核）。

## 5. 组件消融

比值 = 去掉该组件后的 s/Mtok ÷ 全套的 s/Mtok，大于 1 表示有用。✓ = 显著（合并 95% CI 不含 1）。"没生效" = 这个组件在该配置里根本没干活，所以对它下不了结论。每个任务先列已独立复核的行，下面单独列没复核（或只复核了一部分）的行。

### 5.1 Search-R1 · slime（每项 2 对，两序，第 3–24 步）

| 组件 | 去掉的是什么 | 比值 [95% CI] | 显著 | 基线改配置能拿到吗 | 复核 |
|---|---|---|---|---|---|
| `response_logits` | 只在回答 token 上算最后一层输出 | **1.116** [1.109, 1.122] | ✓ | 否 | 比值已重算 |
| `ticket_admission` | ticket 准入（两边并发都是 854） | 0.996 [0.990, 1.001] | — | 否 | 比值已重算；去掉 ticket 那边的陈旧度（最坏 2，从日志重建）未复核 |
| `weight_sync` | flatten + 按 PP 段并行发送（两边都保留 2 GB 缓冲） | 1.002 [0.996, 1.008] | — | 2 GB 缓冲能（两边都开了），其余不能 | 比值已重算 |
